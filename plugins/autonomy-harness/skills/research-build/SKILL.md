# 调研 → 实现 一条龙

分三个阶段串行执行，阶段间**不停下来等用户**（除非命中规格代定协议中必须拍板的决策）。

## 阶段 1：调研

1. 把用户诉求拆成 2–4 个待回答的技术问题（选型、方案对比、成熟度、与现有技术栈的兼容性）。
2. 联网搜索回答它们，优先近期资料与官方文档；**重大选型**（框架级、难以回头的决策）且 deep-research 工作流可用时，用它做对抗核验级调研。
3. 产出调研结论：每个问题一个明确答案 + 依据来源；方案对比必须收敛到**单一推荐**，不许以"各有优劣"收尾。

## 阶段 2：结论转规格

按 closed-loop 的规格代定协议执行：调研结论直接填充技术选型部分；能默认的全部代定（主流、可逆、贴合现有环境）；只有方向性/花钱/对外/删数据类决策才用带推荐项的选择题一次问完，不回应按推荐执行。规格写入 `PROGRESS.md`。

## 阶段 3：闭环实现

进入 closed-loop 完整流程（定义可执行验证 → 执行-验证循环 → verifier 终审 → 提交）。实现中若发现调研结论与现实不符（依赖装不上、API 已变更），回到阶段 1 针对性补查，修正规格后继续——**修正也是自主完成，不请示**，记入代定决策。

## 汇报格式

```
## 结论
（实现了什么，验证是否通过）
## 选型与依据
（调研收敛出的技术决策，一项一句话+来源）
## 代定决策
（含实现中对调研结论的修正）
## 未尽事项
```
