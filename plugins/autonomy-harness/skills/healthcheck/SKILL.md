# 运维巡检

对当前机器和项目做一轮**只读**体检（巡检本身绝不修改系统状态），按以下清单逐项检查：

## 检查清单

1. **服务存活**：项目有 compose 文件 → `docker compose ps` 全部 Up、无重启循环（RestartCount 异常）；另查 `docker ps` 是否有本项目之外意外退出的容器。无 docker 项目则跳过。
2. **接口探活**：对项目对外端口做 curl 探测（端点从 compose 端口映射、`.env`、README 推断），比对预期响应。
3. **系统资源**：`df -h` 磁盘（任一挂载点 >85% 为异常）、`free -m` 内存、`uptime` 负载（load 持续高于核数为异常）。
4. **错误日志**：`docker compose logs --since 24h` 与 `journalctl -p err --since -24h` 中的 ERROR/Traceback/OOM/panic；同类错误聚合计数，不逐条罗列。
5. **安全更新**：`apt list --upgradable` 中标记 security 的包数量。
6. **项目验证**：项目有 `.harness/verify.sh` → 运行一次，报告绿/红。
7. **异常趋势**：若 `PROGRESS.md` 有上次巡检记录，对比是否恶化（磁盘增速、错误数变化）。

## 汇报格式（结论先行）

```
巡检结论：✅ 全部正常 | ⚠️ N 项需关注 | ❌ N 项异常
（仅列出非正常项，每项：现象 → 证据 → 建议的修复命令，可复制执行）
（全正常时只需一行结论 + 关键指标一览：磁盘 x%、内存 x%、服务 x/x Up）
```

把本次巡检结果（日期、结论、关键指标）追加到 `PROGRESS.md` 的巡检记录节，供下次对比趋势。

## 配合 /schedule 无人值守

被定时任务调用（非交互环境）时：全部正常 → 报告保持一行结论；有异常 → 报告完整异常详情。**巡检只诊断不治疗**——即使异常也不要自行重启服务或删文件，把修复命令写进报告，治疗留给人或显式的修复任务。

## 下一步建议（汇报末尾必附，单个）

发现异常 → 给出 `/autonomy-harness:closed-loop 修复<具体异常>` 供复制；全部正常且尚未配置定时巡检 → 建议用 `/schedule` 把本命令设为每日自动运行。
