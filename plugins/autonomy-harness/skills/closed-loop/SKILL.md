# 闭环执行协议

按以下五步执行用户给定的任务。核心原则：**验证由机器说了算，不靠自我感觉**；**打断用户的唯一合法时点是第 1 步**。

## 1. 规格自动补全（用户只给大概描述，其余你负责）

用户通常只提供一句核心诉求。你的职责是把它扩写成完整规格，而不是让用户补作业：

1. **自行起草完整规格**：目标产出、验收标准、边界（不做什么）、技术选型、阶段划分。凡能用合理默认补全的项**全部直接代定**——代定原则：选主流成熟方案、选可逆方案、选与现有环境一致的方案。
2. **筛出必须用户拍板的决策**，判据是三条之一：方向性且猜错重做代价高；涉及花钱或对外可见；删改用户既有数据。通常 0–3 个，多于 3 个说明你代定得不够。
3. 有需要拍板的项时，用**选择题**一次性问完（每题 2–4 个具体选项，把推荐项放第一个并标注"推荐"及理由），绝不抛开放式问题让用户自己想。用户不回应或不在线时，按推荐项直接执行。
4. 规格（含全部代定项）写入 `PROGRESS.md`，之后执行中不再打断用户。
5. 最终汇报单列一节"代定决策"清单（决策 + 理由），供用户事后纠偏；纠偏成本由逐步 git 提交兜底。

## 2. 定义可执行验证（回路闭合器）

为本任务确定机器可判定的通过/失败检查，写入 `.harness/verify.sh`（或在其中追加）：
- 代码类：测试命令 + 构建/编译退出码 + linter。
- 服务类：启动后健康检查（curl 接口比对预期响应）。
- Web/UI 类：浏览器自动化操作 + 截图/DOM 断言。
- 调研/文档类：无法脚本化时，跳过本步，改用第 4 步的对抗核验作为闭合器。

verify.sh 约定：退出码 0 = 通过，非 0 = 不通过；输出要能定位失败原因。

## 3. 执行—验证循环

实现 → 运行 `.harness/verify.sh` → 失败则读输出、修复、重跑。**验证不通过不得宣告完成**（Stop hook 会强制拦截）。每完成一个可验证的子目标就 git commit 一次，提交信息说明做了什么。

## 4. 独立终审

自己不给自己打分。派 `autonomy-harness:verifier` 子代理做新鲜上下文终审：给它任务规格 + 验收标准，让它独立检查交付物并运行验证。调研/文档类任务改派子代理对关键结论做对抗核验（专职尝试驳倒）。终审发现的问题回到第 3 步。

## 5. 收尾

- 更新 `PROGRESS.md`：完成了什么、验证结果、未尽事项、下一步。
- git commit 最终状态。
- 向用户汇报：先结论（做成了什么、验证是否通过），再关键决策及其依据，最后未尽事项。

## 跨会话续作

新会话接手时：先读 `PROGRESS.md` 和 `git log --oneline -20` 恢复状态，选择下一个未完成项继续，不要重做已完成的工作，也不要仅凭"看起来有进展"就宣告整体完成。
