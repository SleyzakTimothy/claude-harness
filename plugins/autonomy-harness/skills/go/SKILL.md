# 智能路由

用户给出一句话诉求（也可能什么都没给）。你的职责：探测状态 → 决定路径 → **直接执行到底**，汇报时说明路由决策。不要把选择权抛回给用户。

## 探测（快速完成，只读）

1. harness 是否已初始化：`.harness/verify.sh` 与 `PROGRESS.md` 是否存在。
2. git 状态：有无未提交的半成品、最近在做什么。
3. 用户诉求归类（见路由表）。

## 路由表（按序匹配，命中即执行对应技能的完整流程）

| 条件 | 路径 |
|---|---|
| 只是提问/咨询，不涉及改动 | 直接回答，不套任何流程 |
| harness 未初始化 | 先走 `harness-init` 全流程，然后**继续**匹配后面的规则 |
| 没给诉求 | 走 `status` 全流程，末尾必须给出可直接复制的下一步命令 |
| 诉求 = 部署/发布/上线 | 走 `ship` 全流程 |
| 诉求明确但技术路线不清（陌生领域、多方案取舍、猜错重做代价高） | 先调研（联网搜索；重大选型用 deep-research）得出结论 → 把结论转成规格 → 走 `closed-loop` |
| 诉求明确且路线清楚 | 直接走 `closed-loop` 全流程 |

## 纪律

- 一次只选一条主路径，执行到底；绝不输出"你可以用 A 或 B"式的清单。
- 汇报第一句说明路由决策及依据（例如："检测到项目未初始化，先补 harness-init，再进入 closed-loop 实现你的需求"）。
- 子流程内部的全部规则照常适用（closed-loop 的规格代定与选择题、ship 的回滚纪律、Stop hook 验证门控）。
- 路由拿不准时，默认 `closed-loop`——它是泛化能力最强的路径。
